Pokédex 2026 - Documentación de Cambios

1. Corrección del esquema de Base de Datos y Tipado

Al ejecutar el archivo original db_update.sql, nos encontramos con un error 150 "Foreign key constraint is incorrectly formed" al intentar generar la tabla de capturas.

El error ocurría porque el campo id de la tabla pokemon era INT(10) UNSIGNED ZEROFILL, mientras que en capturas y en evoluciones se definía como un INT normal. Cambiamos el SQL para garantizar que ambos tipos coincidieran al milímetro:

-- Código modificado en db_update.sql
CREATE TABLE IF NOT EXISTS capturas (
    id INT PRIMARY KEY AUTO_INCREMENT,
    entrenador_id INT NOT NULL,
    pokemon_id INT(10) UNSIGNED ZEROFILL NOT NULL,  -- ¡Corregido!
    -- ...
);

Posteriormente, cargamos la base de datos con el comando en terminal:

mysql -h 127.0.0.1 -u root -padmin123 pokedex_2026 < db_update.sql

2. Demostración y Test de Índices (Búsquedas Optimizadas)

La Pokedex inicialmente incluía un script para introducir más de 1000 Pokémon generados (llamados MewClone). Para el test de tiempos y comprobar el impacto de un Índice procedí con los siguientes pasos mediante terminal:

Prueba 1: Búsqueda sin Índice

Se hizo un drop (eliminación) del índice, se ejecutó una búsqueda en la API y se midió el tiempo mediante `performance.now()`. El comando utilizado fue:

# Borrando el índice
mysql -e "DROP INDEX idx_pokemon_nombre ON pokemon;" 

# Llamando a la API para medir tiempo
curl -s "http://localhost:5000/api/pokemon/buscar-con-tiempo?filtro=MewClone"

Tiempo de respuesta resultante: ~ 3.11 ms

Prueba 2: Búsqueda con Índice activo

Se recreó el índice B-Tree sobre el campo nombre (CREATE INDEX idx_pokemon_nombre ON pokemon(nombre);) y se volvió a realizar la misma petición de búsqueda rápida.

Tiempo de respuesta resultante: ~ 2.26 ms

Se validó que el uso de un índice disminuye radicalmente los tiempos cuando hacemos búsquedas de texto. Este proceso quedó documentado como se pedía.

4. Transacciones Seguras en BDD

El sistema de intecambio utiliza mecanismos ACID para asegurar que los Pokémon no se duplican, pierden, o se corrompen si hay un corte de conexión a mitad del proceso. Esto se logra con transacciones SQL, que engloban todos los UPDATE de los dueños en un único paquete.

  • await connection.beginTransaction();: Inicia la operación cerrada.
  • Se validan a ambos usuarios por seguridad.
  • Si todo es correcto, se actualizan los IDs intercambiando el propietario de la captura 1 de la BD con el propietario de la captura 2.
  • await connection.commit();: Guarda definitivamente en disco todos los cambios del lote.
  • await connection.rollback();: Si ocurre un error, deshace en el momento cualquier actualización pendiente. Ningún dato quedará dañado.

5. Dependencias y Despliegue Local

Finalmente, instalamos las dependencias Node requeridas y corregimos unos pequeños conflictos en el frontend usando comandos nativos:

# Backend (API / NodeJS / Express)
cd backend
npm install
npm start &   # Ejecutado en segundo plano

# Frontend (React / Vite)
cd frontend
npm install --legacy-peer-deps
npm run dev
